# 2026-06-17 작업 로그

## Today

- `CartItem`이 `userId`만 가지지 않고 `User` 객체를 연관관계로 참조하는 이유를 정리했다.
- DB의 FK와 JPA 객체 연관관계가 같은 관계를 서로 다른 방식으로 표현한다는 점을 확인했다.
- `FetchType.LAZY`와 `FetchType.EAGER`의 조회 시점 차이를 공부했다.
- 장바구니 조회에서 연관 엔티티 접근으로 발생할 수 있는 추가 쿼리와 N+1 가능성을 살펴봤다.

## Learned

- DB는 `user_id`라는 FK로 관계를 저장하지만 JPA는 이를 `User` 객체 연관관계로 추상화한다.
- `LAZY` 연관관계는 엔티티 조회 시 실제 객체 대신 프록시를 두고, 일반 필드가 필요해질 때 조회 쿼리를 실행한다.
- 연관 객체를 필드로 가진다는 사실과 그 객체의 전체 데이터를 즉시 조회한다는 것은 같은 의미가 아니다.
- 지연 로딩은 영속성 컨텍스트가 닫힌 뒤 접근하면 예외가 발생할 수 있어 서비스의 트랜잭션 범위를 고려해야 한다.

## Issue

- 처음에는 `User user`를 선언하면 `CartItem` 조회 시 사용자 전체 데이터가 항상 함께 조회되어 무거워진다고 생각했다.
- 실제로는 `LAZY` 프록시를 통해 필요한 시점까지 조회를 미룬다는 것을 확인하며 객체 연관관계와 조회 전략을 구분해 이해했다.

## Next

- Hibernate SQL 로그를 확인해 연관관계 접근 전후의 쿼리 발생 시점을 직접 검증한다.
- 장바구니 목록 조회에서 N+1이 발생하면 Fetch Join 또는 `@EntityGraph` 적용을 비교한다.
- 엔티티를 직접 반환하지 않고 Response DTO로 변환하는 위치와 트랜잭션 범위를 점검한다.
