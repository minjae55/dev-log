# 2026-07-17 작업 로그

> 관련 글: [[Troubleshooting] k6 부하테스트에서 로그인 세션을 재사용하니 인증이 깨지는 문제](https://min-soon.tistory.com/112)

## Today

- 협의 목록 조회 k6 시나리오를 "VU당 로그인 1회 + 반복 조회"로 최적화하다가, 반복 조회의 대부분이 401로 실패하는 문제를 만났다.
- curl 재현, 동시 접속 재현으로도 원인을 못 찾았고, 실패 응답을 직접 출력해서야 401(인증 실패)이라는 걸 확인했다. 원인은 k6의 자동 쿠키 저장소가 기대와 다르게 동작한 것이었고, 로그인 응답에서 쿠키 값을 직접 꺼내 매 요청에 명시적으로 실어 보내는 방식으로 해결했다.
- 시드 스크립트(`DataSeeder`)를 400줄짜리 단일 클래스에서 `FoundationSeeder`/`UserSeeder`/`ProductSeeder`/`TradeSeeder`/`OrderSeeder`/`CartSeeder`로 도메인별 분리 리팩토링했다.
- 주문 생성 API 부하테스트를 진행했다. 재시딩 직후 첫 테스트에서 p95가 1.44초로 목표(800ms)를 크게 초과했는데, 반복 테스트해보니 콜드 스타트 문제였고 이후 안정적으로 p95 235~370ms 범위로 나와 목표를 통과했다.
- 주문 생성 중 가끔(0.1~0.2%) 500 에러가 발생하는 걸 발견했다. curl로 재현을 시도하다 Windows Git Bash의 JSON 따옴표 인코딩 문제에 걸려 헛다리를 짚었고, 진짜 원인은 아직 못 찾았다(에러율 기준은 통과해서 우선순위를 낮춰 보류함).

## Learned

- k6의 VU별 자동 쿠키 유지가 항상 기대한 대로 동작하는 건 아니다. "프레임워크가 알아서 해줄 것"이라는 가정은 검증 없이 믿으면 안 된다.
- 원인을 못 찾을 때는 추측을 쌓기보다 실패 응답을 직접 출력해서 사실을 확보하는 게 훨씬 빠르다.
- 콜드 스타트는 서버 전체뿐 아니라, 특정 API가 처음 실행될 때(그 API가 쓰는 쿼리/코드 경로가 처음 JIT 컴파일될 때)도 개별적으로 발생할 수 있다. 재시딩 직후 첫 테스트 결과를 그대로 믿으면 안 되고, 여러 번 반복해서 일관된 값인지 확인해야 한다.
- 커넥션 풀 크기와 동시 사용자 수가 정확히 같다고 해서 병목이 없는 건 아니지만, VU가 순차적으로(응답을 기다렸다가 다음 요청을 보내는 방식) 동작한다면 이론상 동시 커넥션 수가 VU 수를 넘지 않는다 — 실제 병목 원인은 섣불리 단정하지 말고 데이터(CPU 사용률 등)로 확인해야 한다.

## Troubleshooting

- k6 반복 조회 시 401 에러 — k6 자동 쿠키 저장소 대신 로그인 응답에서 쿠키를 직접 꺼내 헤더에 실어 보내는 방식으로 해결.
- 시드 장바구니 수량이 상품 MOQ보다 항상 작게 생성되어 주문 생성이 100% 실패하던 문제 — 옵션의 재고와 MOQ를 확인해서 조건을 만족하는 수량으로 생성하도록 `CartSeeder` 수정.
- 주문 생성 부하테스트 첫 실행에서 p95 1.44초로 목표 초과 — 콜드 스타트로 판단, 반복 테스트로 재확인 후 목표 통과 확인.
- 주문 생성 중 간헐적 500 에러 재현 시도 중 curl 자체의 JSON 인코딩 문제를 만나 원인 조사가 지연됨 — 아직 미해결, 우선순위 낮춰 보류.
