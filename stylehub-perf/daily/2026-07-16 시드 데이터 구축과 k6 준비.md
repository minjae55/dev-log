## Today

- Java Faker(`datafaker`)를 이용해 부하테스트용 시드 데이터 생성 스크립트(`DataSeeder`, Spring `CommandLineRunner`)를 처음부터 만들었다.
- FK 의존성 순서(Category/Company → Brand/User → Product → SourcingRequest → Quote/QuoteItem → Negotiation/Contract/ContractItem → Order/OrderItem)를 지키면서, 매 단계를 소규모(5~30개)로 먼저 검증한 뒤 다음 단계로 넘어가는 방식으로 진행했다.
- 검증이 끝난 뒤 실제 부하테스트 규모(상품 1만 건, 주문 2만 건 등)로 숫자를 키웠고, 그 전에 Hibernate 배치 insert 설정(`hibernate.jdbc.batch_size`, `order_inserts`)과 MySQL 드라이버 옵션(`rewriteBatchedStatements=true`)을 추가해서 대량 insert 성능을 미리 수정했다.
- API 구조를 살펴보며, 주문 생성 API가 상품 ID가 아니라 장바구니 항목 ID(`cartItemIds`)와 배송지(`addressId`)를 요구한다는 걸 확인했고, 결제 confirm API는 실제 토스페이먼츠 `paymentKey`가 필요해서 순수 부하테스트로 직접 두드리기 어렵다는 것도 파악했다.

## Learned

- DB 외래키 제약 때문에 시드 데이터는 "아무것도 참조하지 않는 것부터 → 참조하는 것" 순서로 만들어야 한다. (Company 없이 User를 만들 수 없는 것과 같은 이치.)
- `CommandLineRunner`는 서버가 켜질 때마다 실행되므로, 재시작마다 데이터가 중복 생성되지 않게 "이미 데이터가 있으면 건너뛰기" 가드가 필요하다. 이 가드를 이해 없이 지웠다가 `Duplicate entry` 에러를 겪고 나서야 왜 필요한지 제대로 이해했다.
- `saveAll()`을 호출해도 Hibernate는 기본적으로 한 줄씩 INSERT를 보낸다. 대량 데이터를 저장할 땐 `rewriteBatchedStatements=true`(드라이버 옵션)와 `hibernate.jdbc.batch_size`(Hibernate 옵션) 둘 다 켜야 진짜로 배치 처리가 된다.
- k6는 로그인 시 받은 쿠키를 같은 가상유저 안에서 자동으로 유지해준다는 걸 알게 되어, 별도 토큰 관리 없이 "로그인 → 인증이 필요한 API" 순서로 스크립트를 짤 수 있었다.

## Troubleshooting

- `CommandLineRunner`의 중복 방지 가드를 이해 없이 주석 처리했다가, 재시작할 때마다 같은 `business_number`로 회사를 다시 만들려고 시도해서 unique 제약 위반 에러가 났다. 가드를 원복하고, 반쯤 쌓인 데이터를 정리한 뒤 다시 실행해서 해결했다.
- 새 단계(예: Product, Contract)를 코드에 추가할 때마다, 이전 실행에서 쌓인 데이터가 남아있으면 가드에 걸려 새 코드가 아예 실행되지 않는 문제를 반복적으로 겪었다. 이후로는 "새 단계 추가 → 관련 테이블 전부 삭제(자식 테이블부터) → 재실행 → 확인" 사이클을 고정 패턴으로 삼았다.
- `createProducts` 메서드에서 중괄호를 하나 더 입력해서 그 아래 메서드들이 클래스 밖으로 밀려나는 컴파일 에러를 겪었다. 괄호 짝을 다시 맞춰서 해결했다.
