## Today

- 재견적/재계약 버전 체이닝(V-Chaining) 로직에서 `resolveRootQuote`/`resolveRootContract`가 지연 로딩된 `parentQuote`/`parentContract`를 while 루프로 반복 접근하며 체인 깊이만큼 쿼리를 반복 실행하는 것을 발견했다.
- 체인 깊이(1/5/10/20/50)별 견적을 SQL로 미리 만들어두고, 깊이별 응답시간을 curl로 재서 깊이에 비례해 응답시간이 늘어나는 걸 확인했다(수정 전 D50 278ms).
- `QuoteRepository`/`ContractRepository`에 `WITH RECURSIVE` 재귀 CTE 쿼리를 추가해 체인 순회를 DB 왕복 1회로 줄였다. 같은 방식으로 재검증한 결과, 깊이와 무관하게 응답시간이 평평해졌다(D50 59ms).
- 진짜 대용량(최소 1천만 건) 환경에서의 병목 진단 연습을 시작했다. `negotiations` 테이블(인덱스 없음)을 SQL 자기 복제로 1,658만 건까지 부풀렸다.
- 협의 목록 조회가 99초 넘게 걸리다 결국 클라이언트 연결이 끊기는 것을 확인하고, 슬로우 쿼리 로그와 `EXPLAIN`으로 원인을 진단했다 — 풀스캔(`type: ALL`) + filesort.
- 복합 인덱스(`buyer_id, updated_at` / `seller_id, updated_at`)를 추가했지만 `EXPLAIN` 결과가 그대로였다. 원인은 Spring Data JPA의 연관관계 기반 메서드(`findByBuyer_UserIdOrSeller_UserId...`)가 `users` 테이블과 조인해서 간접적으로 필터링하는 SQL로 번역되어, negotiations 자체의 인덱스를 쓸 수 없는 구조였기 때문이었다.
- `negotiations` 컬럼을 직접 필터링하는 네이티브 `UNION` 쿼리로 재작성하고 페이지네이션을 추가했다(16.9초로 개선). 이후 특정 사용자의 매칭 행이 13만 건 넘는 걸 확인하고, `UNION` 각 조각에도 `LIMIT`을 걸어 필요한 만큼만 가져오도록 다시 수정해 0.23초까지 줄였다.

## Learned

- Spring Data JPA의 메서드 이름에서 `Buyer_UserId`처럼 연관관계를 타고 들어가는 표현은, 실제 SQL에서는 그 연관 엔티티를 조인한 뒤 조인된 컬럼을 필터링하는 방식으로 번역될 수 있다. 이 경우 원본 테이블 자신의 컬럼에 건 인덱스는 못 쓰인다 — 인덱스를 아무리 잘 설계해도 쿼리 구조가 안 맞으면 무용지물이다.
- 인덱스로 "찾는 것"과 그 결과를 "처리하는 것"은 별개의 병목이다. 인덱스로 빠르게 찾아낸 결과가 크면(13만 건), 그걸 다 모아서 정렬한 뒤 자르는 구조에서는 여전히 느리다 — 각 단계에서 필요한 만큼만 가져오도록 경계를 둬야 한다.
- `EXPLAIN`은 쿼리를 실제로 실행하지 않고 실행 계획만 보여주므로, 느린 쿼리를 끝까지 기다리지 않고도 원인을 미리 진단할 수 있다.
- 재귀적으로 이어진 자기참조 구조(부모-자식 체인)를 애플리케이션 코드에서 반복 조회하면 체인 길이만큼 DB 왕복이 발생한다. MySQL의 `WITH RECURSIVE` CTE로 이 반복을 DB 내부로 옮기면 왕복을 1회로 줄일 수 있다.

## Troubleshooting

- 인덱스를 추가했는데도 `EXPLAIN` 결과가 그대로였던 문제 — 원인 확인을 위해 negotiations를 조인 없이 직접 필터링하는 별도 쿼리로 `EXPLAIN`을 돌려, 인덱스 자체는 정상이고 쿼리 구조(조인)가 원인임을 증명했다.
- 네이티브 쿼리로 재작성한 뒤에도 16.9초가 남아있던 문제 — 특정 사용자의 매칭 행 수를 직접 세어 13만 건임을 확인하고, `UNION` 각 조각에 `LIMIT`을 걸어 해결했다.
