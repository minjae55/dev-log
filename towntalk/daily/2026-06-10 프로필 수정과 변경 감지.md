# 2026-06-10 작업 로그

## Today
- Backend: 마이페이지 프로필 수정 요청을 별도 DTO로 분리하고, 닉네임, 지역, 알림 설정을 수정하는 `PATCH /api/user/myPage/profile` API를 추가했다. 닉네임 중복은 현재 로그인 사용자를 제외하고 검증했으며, 지역 값은 `sidoId`, `sigunguId`, `dongId` 조합이 실제로 유효한지 `RegionService`를 통해 검증했다. 실제 수정은 Repository 직접 update 쿼리가 아니라 `User` 엔티티의 `updateProfile()` 메서드와 JPA dirty checking을 사용해 처리했다.
- Frontend: 마이페이지 프로필 수정 폼을 백엔드 API contract에 맞춰 연결하고, 저장 후 서버가 응답한 최신 프로필 정보를 화면 상태에 반영하도록 수정했다.

## Learned
- `user.updateProfile(request)`는 그 순간 바로 DB에 update 쿼리를 날리는 것이 아니라, 트랜잭션 안에서 영속 상태의 엔티티 값을 변경하는 메서드다. 실제 update 쿼리는 트랜잭션 종료 시점에 JPA dirty checking으로 실행된다.
- Repository에서 직접 update 쿼리를 작성하면 `SELECT` 없이 `UPDATE`만 실행할 수 있어 쿼리 수는 줄어들 수 있다. 하지만 현재처럼 닉네임 중복 검증, 지역 검증, 사용자 존재 확인, 엔티티 상태 변경이 함께 있는 흐름에서는 엔티티를 조회한 뒤 도메인 메서드로 변경하는 방식이 더 읽기 쉽고 유지보수하기 좋다.
- 프로필 수정에서 지역을 받을 때는 단순히 `dongId`만 받는 것보다 현재 테이블 구조에 맞춰 `sidoId`, `sigunguId`, `dongId`를 받고, 서버에서 조합 검증을 하는 방식이 현재 프로젝트 구조와 잘 맞는다.
- 프론트에서 지역 select를 제어하더라도 서버 검증은 반드시 필요하다. 클라이언트 값은 신뢰할 수 없기 때문에 최종 정합성 검증은 백엔드에서 처리해야 한다.

## Troubleshooting
- `user.updateProfile(request)`와 Repository 직접 update 중 어떤 방식을 선택할지 고민했다.
  - 직접 update는 쿼리 수를 줄일 수 있지만, 도메인 변경 로직이 Repository 쿼리 안으로 흩어질 수 있다.
  - 현재 기능은 성능 병목 가능성이 낮고, 프로필 변경 규칙을 엔티티 메서드에 모아두는 편이 더 명확하다고 판단했다.
- `CommentService`를 찾지 못하는 `ClassNotFoundException`이 발생했다.
  - 실제 소스에는 `CommentService`가 존재했기 때문에 코드 삭제 문제가 아니라 빌드 캐시나 실행 환경이 최신 compiled class를 못 읽는 문제로 판단했다.
  - Gradle clean/test 또는 IntelliJ 캐시 초기화 후 정상 동작을 확인했다.
