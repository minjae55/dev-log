# 2026-06-07 작업 로그

## Today
- Backend: 게시글 최신 목록 조회를 카테고리 중복 없이 최신 3개만 내려주도록 QueryDSL 서브쿼리 기반으로 개선하고, 게시글 목록/상세 응답에 작성 시간, 댓글 수, 좋아요 수를 포함하도록 DTO와 조회 쿼리를 확장했으며, 게시글 좋아요 토글 API를 추가해 좋아요 저장/취소 후 최종 `liked`, `likeCount`를 응답하도록 구성했다.
- Frontend: 메인 피드와 게시글 상세 화면에 작성 시간, 댓글 수, 좋아요 수를 연결하고, 좋아요 버튼 클릭 시 서버 응답을 기준으로 좋아요 상태와 개수를 즉시 반영하도록 수정했으며, 댓글 작성/수정/삭제 후 상세 화면의 댓글 수가 새로고침 없이 갱신되도록 상태를 동기화했다.

## Learned
- 좋아요 기능을 만들면서 `PostController`에 엔드포인트를 추가할지, `PostLikeController`로 분리할지 고민했고, URL은 게시글 하위 리소스로 유지하되 코드 구조는 좋아요 관심사 기준으로 분리하는 방향을 선택했다.
  - https://min-soon.tistory.com/79
- 기존 프로젝트가 `Repository / RepositoryImpl / JpaRepository / QueryRepository` 구조를 사용하고 있어, 좋아요 repository도 같은 패턴으로 맞추는 것이 프로젝트 일관성 측면에서 더 낫다고 판단했다.
- `JPAExpressions`와 별칭용 `QPost postSub`를 사용하면 카테고리별 최신 게시글처럼 그룹별 대표 row를 조회할 수 있다.
- QueryDSL `Projections.constructor()`는 record 생성자 순서와 타입이 정확히 맞아야 하며, `count()` 결과는 보통 `Long`으로 맞추는 것이 안전하다.
- `Expressions.constant(0)`은 조회 결과에 고정값 0을 넣는 임시 projection이며, 실제 댓글 수/좋아요 수가 필요하면 count 서브쿼리로 대체해야 한다.
- 프론트에서 서버 응답 없이 `+1`로 추측하는 방식보다, 서버가 내려준 최종 `likeCount`를 source of truth로 반영하는 방식이 더 안전하다.

## Troubleshooting
- 상세 조회에서 `No constructor found for ReadPostDetail` 오류가 발생했다.
  - 원인은 QueryDSL projection 타입이 `Long`, `Integer`로 섞였는데 DTO record는 다른 타입 조합을 기대했기 때문이다.
  - `count()` 기반 필드는 `long`/`Long`으로 맞추고, 임시 고정값은 `Expressions.constant(0L)`처럼 타입을 명확히 맞춰야 한다.
- 좋아요를 눌렀을 때 메인 피드가 사라지는 문제가 있었다.
  - 좋아요 실패 메시지를 게시글 로드 실패 상태인 `postLoadError`에 넣어서 목록 렌더링 조건이 막힌 것이 원인이었다.
  - 좋아요 액션 전용 에러 상태를 분리해 피드 목록은 유지되도록 수정했다.
- 좋아요 row는 저장됐지만 상세 화면 좋아요 수가 0으로 보였다.
  - 화면은 `posts.like_count`를 보고 있었고, 좋아요 저장 로직은 `likes` 테이블에만 insert하고 있었다.
  - 좋아요 수는 `likes` 테이블 count를 조회하거나, 별도 카운터 컬럼을 함께 갱신해야 한다는 점을 확인했다.

## Blocker
- `frontend/package-lock.json`에 의도하지 않은 변경이 남아 있어 커밋 대상에서 제외해야 한다.
- 좋아요 토글은 동작하지만, 중복 요청이나 동시성 상황에서는 DB unique constraint와 서비스 레벨 예외 처리를 더 보강할 필요가 있다.
