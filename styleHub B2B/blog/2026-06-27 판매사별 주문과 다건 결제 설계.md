# [Architecture] 판매사별 주문은 나누고, 결제는 한 번에 처리하기까지

국내 여성의류 B2B 플랫폼의 주문 기능을 구현하면서 장바구니 상품을 판매 회사별로 묶어 주문을 생성했다.

예를 들어 바이어가 A 회사 상품과 B 회사 상품을 함께 구매하면 장바구니에서는 한 번에 선택할 수 있지만, 주문은 다음과 같이 두 개가 생성된다.

```text
장바구니
├─ A 회사 상품 2개
└─ B 회사 상품 1개

주문 생성 결과
├─ Order 1: A 회사 상품 2개
└─ Order 2: B 회사 상품 1개
```

판매 회사가 다르면 배송비, 무료 배송 기준, 출고 처리, 주문 상태와 정산 주체가 모두 달라질 수 있기 때문이다. 따라서 주문을 회사별로 분리한 결정 자체는 자연스러웠다.

그런데 주문 목록을 연결한 뒤 새로운 문제가 보였다. 회사별로 생성된 주문마다 `결제하러 가기` 버튼이 있었고, 바이어는 같은 장바구니에서 함께 주문한 상품도 결제를 여러 번 진행해야 했다.

백엔드의 주문 처리 단위와 사용자가 기대하는 결제 단위가 반드시 같지는 않았다.

## 주문을 다시 하나로 합치면 안 될까?

처음에는 결제를 한 번만 받기 위해 여러 주문을 하나로 합치는 방법을 생각했다. 하지만 하나의 주문에 여러 판매 회사가 포함되면 이후의 책임이 불명확해진다.

- 어느 회사의 배송비를 적용해야 하는가?
- A 회사는 출고했지만 B 회사는 준비 중이라면 주문 상태는 무엇인가?
- 한 회사의 상품만 취소하거나 환불하면 주문 금액을 어떻게 관리할 것인가?
- 판매 대금은 어느 회사에 얼마씩 정산해야 하는가?

결제를 편하게 만들기 위해 주문의 경계를 무너뜨리면 배송, 취소, 환불과 정산 로직이 더 복잡해진다.

따라서 **주문은 판매 회사별로 유지하고, 결제만 여러 주문을 묶어 처리하는 방향**이 적절하다고 판단했다.

## 고민했던 세 가지 방법

### 1. 주문마다 각각 결제하기

가장 단순한 방법이다. 기존 단건 Checkout API를 그대로 사용할 수 있고 구현 범위도 작다.

하지만 주문이 세 개 생성되면 바이어는 결제창도 세 번 열어야 한다. 같은 구매 흐름에서 생성된 주문이라는 사용자 경험을 전혀 반영하지 못한다.

### 2. 여러 주문을 하나의 주문으로 병합하기

결제는 한 번만 하면 되지만 판매 회사별 배송, 상태와 정산 경계가 사라진다. 주문 이후의 처리 비용이 너무 커지는 방식이었다.

### 3. 주문은 분리하고 결제 대상을 묶기

각 `Order`는 그대로 유지하면서 Checkout 요청에서 여러 `orderId`를 전달하는 방식이다.

```text
Order A ─┐
Order B ─┼─ Payment 1건
Order C ─┘
```

이 구조에서는 주문별 배송과 상태를 독립적으로 관리하면서도 사용자는 한 번만 결제할 수 있다. 현재 서비스에 가장 적합한 방향이라고 판단했다.

## 단건과 다건 요청을 하나로 통일하기

기존 단건 결제 경로는 다음과 같았다.

```text
/checkout?orderId=1
```

다건 결제를 추가하면서 단건과 다건을 별도 흐름으로 만들 수도 있었다. 하지만 단건 결제는 주문 ID가 하나인 다건 결제로 볼 수 있다.

그래서 프론트 경로를 `orderIds`로 통일했다.

```text
단건: /checkout?orderIds=1
다건: /checkout?orderIds=1,3,5
```

Checkout에서는 문자열을 주문 ID 배열로 변환한다.

```tsx
const orderIds = orderIdsParam
  .split(",")
  .map(Number)
  .filter((orderId) => Number.isInteger(orderId) && orderId > 0);
```

이렇게 하면 단건과 다건을 위한 조건문과 상태를 따로 관리하지 않아도 된다.

## 프론트를 먼저 연결하며 사용한 임시 방식

아직 백엔드에는 다건 Checkout API가 없기 때문에 기존 단건 조회 API를 여러 번 호출하고 결과를 합산했다.

```tsx
const responses = await Promise.all(
  orderIds.map((orderId) =>
    api.get<OrderCheckoutResponse>(`/checkout/preview/${orderId}`)
  )
);

const totalAmount = responses.reduce(
  (total, response) => total + response.totalAmount,
  0
);
```

이 방식은 다건 선택 화면과 Checkout 합산 결과를 먼저 확인하기에는 편리하다. 하지만 최종 구조로 사용하기에는 문제가 있다.

- 선택한 주문 수만큼 HTTP 요청이 발생한다.
- 요청 일부만 실패하면 전체 결제 가능 여부를 일관되게 판단하기 어렵다.
- 모든 주문의 소유자와 상태를 한 번에 검증할 수 없다.
- 결제 직전에 주문 상태가 변경되는 경쟁 조건을 통제하기 어렵다.

따라서 `Promise.all`은 프론트 흐름을 검증하기 위한 임시 구현으로만 사용하고, 백엔드 다건 API로 교체할 예정이다.

## 다음 백엔드 API의 책임

다건 Checkout 요청은 다음과 같이 주문 ID 목록을 받도록 설계할 수 있다.

```java
public record OrderCheckoutRequest(
        List<Integer> orderIds
) {
}
```

백엔드는 단순히 금액만 더해서는 안 된다. 다음 조건을 한 번에 검증해야 한다.

1. 주문 ID 목록이 비어 있지 않은가?
2. 요청한 주문이 모두 존재하는가?
3. 모든 주문이 로그인한 바이어의 주문인가?
4. 모든 주문이 `PENDING` 상태인가?
5. 이미 결제되었거나 취소된 주문이 포함되어 있지 않은가?

조회된 주문 개수와 요청한 ID 개수가 다르면 다른 사용자의 주문이나 존재하지 않는 주문이 포함되었을 가능성이 있으므로 요청 전체를 실패시켜야 한다.

```java
if (orders.size() != request.orderIds().size()) {
    throw new BusinessException(ErrorCode.ORDER_NOT_FOUND);
}
```

검증이 끝난 뒤 상품 금액, 판매사별 배송비와 최종 결제 금액을 계산해 하나의 Checkout 응답으로 내려준다.

## 결제와 주문의 관계도 분리해야 한다

실제 결제까지 연결하려면 하나의 결제 결과가 여러 주문을 참조할 수 있어야 한다.

결제 테이블에 `order_id` 하나만 두면 다건 결제를 표현하기 어렵다. 결제와 주문 사이에 연결 테이블을 두는 방식을 고려할 수 있다.

```text
payments
├─ payment_id
├─ payment_key
├─ total_amount
└─ status

payment_orders
├─ payment_id
└─ order_id
```

결제 승인에 성공하면 연결된 모든 `PENDING` 주문을 `CONFIRMED`로 변경한다. 반대로 일부 주문만 먼저 확정되면 데이터 정합성이 깨지므로 결제 저장, 주문 연결과 상태 변경을 하나의 트랜잭션 경계로 관리해야 한다.

이 부분은 결제 담당 팀원과 인터페이스를 맞춘 뒤 최종 구조를 결정할 예정이다.

## 정리

이번 고민의 핵심은 주문과 결제를 같은 단위로 생각하지 않는 것이었다.

- 주문은 배송, 상태와 정산을 위해 판매 회사별로 분리한다.
- 결제는 사용자의 편의를 위해 여러 주문을 하나로 묶을 수 있다.
- 단건 결제도 주문 ID가 하나인 다건 결제로 통일한다.
- 프론트의 다중 요청은 흐름 검증용으로 사용하고, 최종 검증과 금액 계산은 백엔드 다건 API가 담당한다.
- 하나의 결제와 여러 주문의 관계는 별도의 연결 구조로 표현한다.

처음에는 주문을 회사별로 잘 나누는 것만 생각했다. 하지만 주문 목록을 실제로 사용해보니 백엔드의 처리 단위가 그대로 사용자 경험이 되어서는 안 된다는 점을 알게 되었다.

도메인의 책임은 유지하면서도 사용자가 불필요한 절차를 반복하지 않도록, 주문과 결제의 경계를 분리해 설계하는 것이 이번 작업에서 가장 중요했던 결정이었다.

## 한 줄 회고

**데이터를 나누는 기준과 사용자가 행동하는 기준은 다를 수 있으며, 좋은 설계는 두 기준을 억지로 합치지 않고 연결하는 방법을 찾는 과정이었다.**
