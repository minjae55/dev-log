## Today

- 협의 요청 모달에서 협의 내용을 작성하고 바로 협의 요청을 생성할 수 있도록 백엔드 협의 생성 API와 연동했다.
- 협의 요청 생성 시 기존 진행 중인 협의가 있으면 이어서 사용하고, 없으면 새로운 협의를 생성하도록 협의 생성 로직을 구현했다.
- 셀러 주문 상세에서 택배사와 운송장 번호를 입력해 출고 정보를 등록할 수 있도록 배송 추적 API를 연동했다.
- 셀러 주문 상세 화면의 레이아웃과 버튼, 카드, 상태 표시를 정리해 전체적인 가독성을 개선했다.
- Redis의 동작 방식과 활용 사례를 다시 정리하며 메모리 기반 데이터베이스의 특징과 캐시 활용 방식을 학습했다.

## Learned

- 협의 생성은 단순히 견적 상태만 변경하는 기능이 아니라 협의 내용 저장과 상태 변경이 함께 이루어지는 별도의 업무 흐름이다.
- 협의 생성 API에서 견적 상태까지 함께 변경하도록 책임을 두면 프론트에서 중복으로 상태 변경 API를 호출하지 않아도 된다.
- 진행 중인 협의를 재사용하도록 구현하면 동일한 견적에 여러 개의 협의가 생성되는 문제를 방지할 수 있다.
- 정보가 많은 화면은 레이아웃과 간격만 정리해도 사용성과 가독성이 크게 향상된다.
- Redis는 단순한 캐시가 아니라 메모리 기반 데이터베이스이며, 캐시뿐 아니라 세션 관리, Refresh Token 저장, 실시간 데이터 처리 등 다양한 용도로 활용할 수 있다.

## Troubleshooting

- 협의 버튼을 누르는 즉시 협의 페이지로 이동하는 구조라 협의 요청 확인 모달과 충돌하는 문제가 있었다.
- 협의 생성 API와 견적 상태 변경 API를 모두 호출하면서 동일한 상태 변경이 중복 수행되어 견적 상태 검증 예외가 발생했다.
- 협의 생성 API에서 상태 변경까지 함께 처리하도록 책임을 분리하고 프론트에서는 협의 생성 API만 호출하도록 수정해 중복 상태 변경 문제를 해결했다.
- 셀러 주문 상세 화면은 정보가 많아 위계가 명확하지 않았고, 레이아웃과 간격을 재구성해 가독성을 개선했다.
