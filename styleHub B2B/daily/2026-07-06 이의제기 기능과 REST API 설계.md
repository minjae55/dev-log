# 2026-07-06 이의제기 기능과 REST API 설계

> 관련 글: [REST API를 설계 고민 - 이의제기 API는 주문 기준일까, 이의제기 기준일까?](https://min-soon.tistory.com/108)

## Today

- 바이어와 셀러 이의제기 기능의 전체 흐름을 설계하고 생성, 목록, 상세, 답변 API를 구현했다.
- 이의제기 생성은 주문에서 시작되지만 이후에는 독립적인 리소스로 관리된다는 점을 고려해 REST API 구조를 재설계했다.
- 바이어·셀러 전용 Controller를 분리하고 권한에 따라 조회와 응답 로직이 동작하도록 구성했다.
- 이의제기 목록, 상세, 답변 등록에 필요한 DTO와 Repository를 추가하고 서비스 계층을 정리했다.
- 주문 상세에서 이의제기 작성 모달을 통해 접수할 수 있도록 UI를 구성하고 생성 API와 연결했다.
- 바이어 대시보드에서 이의제기 목록으로 이동하는 화면과 라우팅을 연결했다.
- 주문 상세 경로와 이의제기 목록 경로가 충돌하던 라우팅을 수정해 각각 올바른 화면으로 이동하도록 정리했다.

## Learned

- 이의제기는 주문에서 생성되지만 생성 이후에는 고유한 식별자를 가지므로 생성 API만 `/orders/{orderId}/disputes`에 두고, 이후 목록·상세·답변은 `disputes` 리소스로 분리하는 것이 REST 관점에서 더 자연스럽다.
- URL은 데이터베이스의 FK 관계보다 현재 API가 어떤 리소스를 대상으로 동작하는지를 기준으로 설계하는 것이 유지보수성과 가독성이 높다.
- `orders/:id`와 같은 동적 라우트는 `orders/disputes` 같은 고정 경로보다 뒤에 선언해야 의도한 화면으로 정상 이동한다.
- 바이어와 셀러의 역할이 다른 기능은 Controller를 분리하면 권한 검증과 책임이 명확해지고 코드 구조도 단순해진다.

## Troubleshooting

- 처음에는 생성, 조회, 답변 API를 모두 주문 기준(`/orders/{orderId}`)으로 설계했지만, 이의제기 생성 이후에는 주문보다 이의제기 자체를 대상으로 하는 기능이 대부분이라 URL 구조가 불필요하게 복잡해졌다.
- 생성은 주문 기준으로 유지하고, 이후 기능은 이의제기 리소스를 기준으로 분리하는 방식으로 API 구조를 재설계했다.
- 바이어 대시보드에서 `/buyer/orders/disputes`로 이동하면 `orders/:id` 라우트가 먼저 매칭되어 `"올바르지 않은 주문 번호입니다."` 오류가 발생했다.
- `orders/disputes`와 `orders/disputes/:disputeId` 경로를 `orders/:id`보다 먼저 선언해 라우팅 충돌을 해결했다.
