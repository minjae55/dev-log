- 재고 부족, MOQ 미달, 샘플 주문 제한처럼 Checkout에서 발생할 수 있는 검증 실패를 어떤 방식으로 프론트에 내려줄지 고민했다.
- 검증 조건마다 DTO를 따로 만들지 않고, 검증 실패 상품을 표현하는 공통 DTO와 검증 실패 응답 DTO로 구조를 단순화했다.
- `CheckoutValidationException`과 전용 `ExceptionHandler`를 추가해 검증 실패 상품 목록을 `ApiResponse`의 `data.invalidItems`로 내려주도록 정리했다.
- 프론트 Checkout 화면에서 `CHECKOUT_001` 응답을 일반 에러와 분리해, 어떤 상품이 왜 주문 불가능한지 상품명·옵션·요청 수량·가능 수량으로 표시하도록 수정했다.
- 이후 이 검증 안내가 Checkout에서만 보이는 것이 맞는지 다시 고민했고, Cart에서 먼저 사전 안내하고 Checkout은 최종 방어선으로 두는 방향이 더 자연스럽다고 정리했다.

## Learned

- Checkout 검증 실패는 단순한 서버 오류가 아니라 사용자가 수정할 수 있는 비즈니스 상태이므로, 구체적인 실패 항목을 내려주는 것이 중요하다.
- `OUT_OF_STOCK`, `MOQ_NOT_MET`, `SAMPLE_LIMIT_EXCEEDED`처럼 검증 종류는 여러 개여도, 프론트가 필요한 정보는 대부분 상품명, 옵션, 사유, 요청 수량, 가능 수량으로 공통화할 수 있다.
- 첫 번째 검증 실패에서 바로 `throw`하면 사용자는 문제를 하나씩만 알게 된다. 여러 장바구니 상품을 한 번에 검증하는 Checkout에서는 실패 항목을 모아서 반환하는 편이 더 친절하다.
- Cart와 Checkout의 검증 책임은 다르게 봐야 한다. Cart는 사용자가 수량과 선택 상품을 조정하는 화면이므로 사전 안내에 적합하고, Checkout은 결제 직전 서버 기준으로 다시 확인하는 최종 검증 지점이다.

## Troubleshooting

- Checkout 진입 시 `quantity > stockQuantity` 조건에서 `OUT_OF_STOCK` 예외가 발생했지만, 프론트에서는 모든 조회 실패를 같은 메시지로 처리하고 있었다. 이 때문에 사용자는 어떤 상품의 재고가 부족한지 알 수 없었다.
- 검증마다 별도 DTO를 만들면 구조가 과하게 늘어날 수 있어, `CheckoutInvalidItemResponse` 하나로 상품별 실패 정보를 표현하고 `CheckoutValidationErrorResponse`에서 목록으로 감싸도록 정리했다.
- 기존 `validateCartItem()`은 검증 실패 시 즉시 `BusinessException`을 던졌지만, 변경 후에는 실패 항목을 리스트에 모으고 마지막에 `CheckoutValidationException`을 던지도록 수정했다.
- 프론트에서는 `code === "CHECKOUT_001"`인지 확인한 뒤 `data.invalidItems`를 읽어 일반 에러 페이지가 아니라 검증 실패 상품 목록을 보여주도록 분기했다.
