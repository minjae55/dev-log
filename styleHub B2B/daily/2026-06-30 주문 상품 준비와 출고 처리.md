## Today

- 셀러 주문에서 회사 대표와 직원의 조회 및 처리 범위를 구분했다.
- 직원은 자신이 담당하는 상품이 포함된 주문 목록을 조회하되, 주문 상세에서는 같은 주문에 포함된 전체 상품과 준비 진행률을 확인하도록 변경했다.
- 직원은 본인 담당 상품만 `READY`로 변경하고, 대표는 주문의 모든 상품을 일괄 준비 완료 처리할 수 있도록 구성했다.
- 주문 상품 준비가 시작되면 주문 상태를 `CONFIRMED → PREPARING`으로 변경하고 상태 이력을 저장하도록 연결했다.
- 모든 주문 상품이 `READY`일 때 택배사와 운송장 번호를 등록하고 주문 상태를 `SHIPPED`로 변경하는 출고 흐름을 구현했다.
- 운송장 등록은 같은 판매 회사의 대표와 직원 모두 처리할 수 있도록 하고, 다른 회사 사용자의 접근은 차단했다.

## Learned

- 한 주문에 여러 담당자의 상품이 포함될 수 있으므로 주문 전체 조회 권한과 개별 상품 수정 권한을 같은 기준으로 제한하면 협업에 필요한 진행 상황을 파악하기 어렵다.
- 직원의 주문 참여 여부를 먼저 검증한 뒤 전체 상품을 조회하고, 상품별 처리 가능 여부를 별도 값으로 전달하면 조회와 변경 권한을 명확히 분리할 수 있다.
- `OrderItem.itemStatus`는 상품별 준비 여부를 표현하고 `Order.status`는 주문 전체의 진행 단계를 표현하므로 두 상태의 책임을 분리해야 한다.
- 출고 정보 등록은 새로운 주문을 만드는 작업이 아니라 기존 주문의 운송 정보와 상태를 변경하는 작업이므로 `PATCH`가 적절하다.
- 엔티티가 HTTP 요청 DTO에 의존하지 않고 필요한 값만 전달받도록 구성하면 다른 서비스와 배치 작업에서도 도메인 메서드를 재사용하기 쉽다.

## Troubleshooting

- 직원 계정으로 주문 상세를 조회하면 본인 담당 상품만 표시되어 다른 담당자의 준비 여부와 주문 전체 진행 상황을 확인할 수 없었다.
- 상세 조회에서도 담당자 조건으로 `OrderItem`을 필터링해 조회 범위와 수정 권한을 하나의 조건으로 처리한 것이 원인이었다.
- 모든 상품이 `READY`인데 출고 정보 입력 영역이 나타나지 않는 기존 주문도 확인했다. 상품 준비 상태는 완료됐지만 주문 상태가 `CONFIRMED`에 남아 있어, 화면 노출 조건인 `PREPARING`과 일치하지 않은 것이 원인이었다.

- 문자열로 저장하는 택배사 정보를 추적 API 규격에 맞는 enum 또는 코드로 관리할지 검토한다.
