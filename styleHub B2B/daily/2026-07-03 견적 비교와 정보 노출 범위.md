# 2026-07-03 작업 로그

## Today

- 소싱 요청을 기준으로 셀러가 견적을 작성하고, 바이어와 셀러가 각각 자신의 견적 목록과 상세 내용을 조회하는 흐름을 연결했다.
- 견적 생성, 바이어 목록, 셀러 목록, 상세 조회, 상태 변경의 책임을 서비스별로 정리하고 견적 참여자와 회사 권한을 검증했다.
- 바이어가 같은 소싱 요청에 도착한 여러 견적의 금액, 납기, 샘플 제공 여부를 한 화면에서 비교할 수 있도록 목록을 요청 단위로 그룹화했다.
- 견적 채택, 거절, 협의 요청, 샘플 결제로 이어지는 행동을 목록에서 처리할 수 있도록 연결하고 버튼의 중요도에 따라 시각적 위계를 조정했다.
- 계약 전 1:1 우회를 방지하기 위해 바이어 견적 목록과 상세 화면에서 실제 공급 회사명과 담당자명을 숨기고 `공급업체 A/B/C` 형태로 표시했다.
- 견적의 거래 진행 상태와 문서 열람 여부는 의미가 다르므로 하나의 `status`로 표현하지 않고 별도 열람 상태로 관리해야 함을 확인했다.

## Learned

- 프론트에서 회사명과 담당자명을 가리는 것만으로는 정보 비노출이 보장되지 않는다. 바이어 전용 응답 DTO에서도 해당 필드를 제외해야 네트워크 응답을 통한 노출을 막을 수 있다.
- `SUBMITTED`, `NEGOTIATING`, `SAMPLE_REQUESTED`는 견적의 업무 진행 상태이고, `열람/미열람`은 사용자의 문서 확인 여부다. 두 개념을 같은 컬럼으로 관리하면 상태 전이와 화면 표시가 서로 꼬일 수 있다.
- 열람 여부는 단순 Boolean보다 `viewedAt`으로 저장하면 열람 여부와 최초 열람 시각을 함께 표현할 수 있다.
- 비교 화면에서는 모든 행동을 같은 크기의 버튼으로 나열하기보다 최종 확정을 주 행동으로 두고 협의, 거절, 샘플 결제를 보조 행동으로 구분해야 사용자가 판단하기 쉽다.
- 견적 목록과 상세 조회가 느릴 때는 컴퓨터 성능만 의심하기보다 원격 DB의 네트워크 왕복, 지연 로딩으로 발생하는 추가 쿼리, 전체 목록 조회 여부를 함께 확인해야 한다.

## Troubleshooting

- 견적 목록에 공급사명과 담당자명을 그대로 표시하면 계약 전 당사자 간 직접 거래를 유도할 수 있다는 문제를 발견했다.
- 처음에는 공급사 열을 제거했지만 여러 견적을 비교할 때 각 행을 구분하기 어려웠다. 실제 정보 대신 소싱 요청 안에서만 유효한 `공급업체 A/B/C` 별칭을 사용하도록 수정했다.
- 견적 상태 열에 `샘플 진행` 같은 업무 상태를 표시했으나, 목록에서 바이어에게 더 필요한 정보는 새 견적을 확인했는지 여부라고 판단했다.
- 현재 엔티티와 DTO에는 열람 정보가 없으므로 상태 문구만 `미열람`으로 바꾸는 방식은 상세 조회 후에도 값이 바뀌지 않는 잘못된 구현이 된다. `viewedAt`을 별도 저장하고 상세 조회 시 최초 열람을 기록하는 방향으로 정리했다.
- 견적 목록의 버튼이 많아 주요 행동이 구분되지 않는 문제는 버튼을 삭제하기보다 색상, 테두리, 크기로 역할을 구분해 해결했다.
