# 2026-06-27 작업 로그

> 관련 글: 작성 예정

## Today

- 장바구니에서 재고 수량을 입력 상한으로 제한하던 방식을 다시 검토했다.
- 사용자가 원하는 수량은 입력할 수 있도록 허용하되, 현재 재고보다 몇 개를 초과했는지 안내하고 주문 선택과 Checkout 진행을 제한하도록 수정했다.
- 주문 목록에서 상품 정보가 임시 문구로 표시되고, 주문 카드를 펼친 뒤에야 실제 상품명이 나타나는 흐름을 개선했다.
- 주문 목록 응답에 대표 상품명, 품목 수, 총수량을 추가하고 생성일 기준 최신순으로 조회하도록 변경했다.
- 주문마다 상품을 개별 조회하지 않도록 주문 목록과 주문 상품을 각각 한 번씩 조회한 뒤 주문 ID 기준으로 그룹화했다.
- 판매 회사별로 분리된 결제 대기 주문을 사용자가 한 번에 선택할 수 있도록 주문 선택, 전체 선택, 선택 금액 표시, 다건 Checkout 이동 UI를 구현했다.
- 단건과 다건 Checkout 경로를 `orderIds` 형식으로 통일하고, 기존 단건 Checkout 응답을 프론트에서 합산해 다건 결제 화면을 우선 확인할 수 있도록 연결했다.

## Learned

- 장바구니는 입력을 강제로 막는 화면보다 주문 가능 여부와 수정 이유를 명확히 알려주는 화면에 가깝다.
- 주문 목록 DTO에는 전체 상세 정보가 아니라 사용자가 목록을 구분하는 데 필요한 대표 상품명, 품목 수, 총수량 정도를 포함하는 것이 적절하다.
- 주문과 주문 상품을 주문별로 반복 조회하면 주문 수만큼 쿼리가 늘어날 수 있다. 필요한 주문 상품을 한 번에 조회한 뒤 애플리케이션에서 그룹화하면 조회 횟수를 일정하게 유지할 수 있다.
- B2B 주문은 배송, 처리 상태, 정산 주체 때문에 판매 회사별로 분리해야 하지만, 결제 경험까지 주문 단위로 강제할 필요는 없다.
- 단건 결제를 다건 결제의 특수한 경우로 보면 `orderId`와 `orderIds` 흐름을 따로 관리하지 않고 하나의 인터페이스로 통일할 수 있다.

## Troubleshooting

- 배송비 묶음의 일부 상품 수량이 수정되지 않았다. 상품 수량이 MOQ와 같을 때 MOQ를 입력 하한으로 사용하면서 감소와 직접 입력을 막고 있던 것이 원인이었다.
- MOQ와 재고를 수량 입력 제한으로 사용하지 않고, 입력 후 주문 가능 여부를 판단하는 검증 조건으로 변경했다. 재고를 초과하면 초과 수량을 표시하고 해당 상품을 Checkout 대상에서 제외하도록 정리했다.
- 주문 목록 API에는 상품 정보가 없어서 프론트가 `주문 상품 상세는 상세 화면에서 확인`이라는 임시 상품명을 사용하고 있었다. 주문 카드를 펼칠 때 상세 API가 호출된 후에야 실제 상품명으로 교체되어 화면 정보가 갑자기 바뀌었다.
- 목록 응답에 대표 상품 정보를 추가하되 주문별로 `OrderItem`을 조회하지 않았다. 전체 주문 ID에 해당하는 주문 상품을 한 번에 조회하고 `orderId`로 그룹화해 목록 응답을 생성했다.
- 주문 목록 최신순 정렬을 위해 `OrderItemRepository`의 정렬 방향을 변경했지만 주문 순서에는 영향이 없었다. 주문 상품 정렬과 주문 목록 정렬은 서로 다른 조회이므로, `OrderRepository`에 `OrderByCreatedAtDesc`를 적용했다.
