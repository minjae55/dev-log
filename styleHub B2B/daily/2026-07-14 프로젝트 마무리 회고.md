- 단순 기능 구현보다 각 기능이 어떤 상태 변화와 사용자 역할을 기준으로 연결되는지가 더 중요하다는 점을 회고했다.
- 판매사별 주문 분리, 주문 상품별 담당자 준비 상태, 견적 기반 샘플 결제, 계약서 전자서명과 PDF 생성, 이의제기 흐름을 프로젝트의 핵심 경험으로 정리했다.
- 프로젝트 이후 고도화 방향으로 K6 기반 부하 테스트와 성능 개선 계획을 정리했다.

## Learned

- API 하나가 정상 동작하는 것과 서비스 흐름이 자연스럽게 이어지는 것은 다르다.
- B2B 거래에서는 바이어, 셀러, 관리자처럼 역할이 나뉘고, 각 단계마다 변경 가능한 상태와 확정되어야 하는 데이터가 다르다.
- 주문, 견적, 계약, 결제, 배송, 이의제기는 독립된 기능처럼 보이지만 실제 서비스에서는 하나의 거래 흐름으로 연결되어야 한다.
- 계약서처럼 거래 증빙이 필요한 데이터는 화면 표시뿐 아니라 PDF 생성, 전자서명, 해시 검증처럼 문서 무결성을 고려해야 한다.
- 프로젝트 후반에는 기능 완성보다 상태 흐름, 권한 검증, 화면 전환, 후처리까지 함께 검증하는 것이 중요했다.

## Troubleshooting

- 프로젝트 중간에 도메인 구조가 변경되면서 DTO, Service, Controller의 책임을 다시 나누어야 했다.
- 공통 응답 구조와 프론트 Axios 처리 방식이 맞지 않아 응답 데이터를 잘못 꺼내는 문제가 있었다.
- 주문과 결제 흐름에서는 단건 주문과 다건 주문, 장바구니 기반 Checkout과 주문 기반 Checkout을 분리할지 통합할지 고민했다.
- 계약서 작성과 서명 흐름에서는 임시 저장, PDF 미리보기, 최종 서명, 해시 검증 시점이 어긋나면서 상태 처리를 다시 정리해야 했다.
- 배송 추적과 이의제기처럼 외부 API나 다른 도메인과 연결되는 기능은 단순 화면 연동보다 권한, 상태 동기화, 후속 처리까지 함께 봐야 했다.
