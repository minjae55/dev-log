# 2026-06-29 작업 로그

> 관련 글: 작성 예정

## Today

- 주문 상세 API에서 주문 상품과 함께 상태 변경 이력을 조회하도록 연결했다.
- `OrderLog` 엔티티를 직접 반환하지 않고 `BuyerOrderLogResponse` DTO로 변환해 필요한 정보만 전달했다.
- 주문 생성 시 최초 `PENDING` 로그를 저장하고, 개발용 결제 완료 시 `CONFIRMED` 로그를 남기도록 구성했다.
- 주문 상세 화면에 `PENDING → CONFIRMED → PREPARING → SHIPPED → DELIVERED → COMPLETED` 전체 진행 단계를 표시했다.
- 완료 단계, 현재 단계, 예정 단계를 구분하고 예정 단계는 회색으로 표현했다.
- 취소, 이의제기, 환불은 정상 진행 단계에 고정하지 않고 실제 발생한 경우에만 표시하도록 분리했다.

## Learned

- `orders.status`는 현재 상태를 빠르게 조회하기 위한 값이고, `order_logs`는 상태가 언제 누구에 의해 변경됐는지 추적하기 위한 데이터다.
- 엔티티를 API 응답에 직접 노출하면 불필요한 연관관계와 지연 로딩 문제가 생길 수 있으므로 응답 DTO로 변환하는 편이 안전하다.
- 상태 이력만 나열하면 사용자가 다음 단계를 알기 어렵고, 전체 단계를 고정하면 예외 상태까지 정상 흐름처럼 보일 수 있다.
- 정상 진행 단계는 전체 타임라인으로 보여주고, 예외 상태는 실제 발생 시 추가하는 방식이 주문 흐름을 가장 명확하게 표현한다.

## Troubleshooting

- 주문 상세 화면에 상태 이력 대신 안내 문구만 표시됐다.
- 프론트 연결 문제로 예상했지만, 상세 API의 `logs` 배열이 비어 있는 것이 원인이었다.
- 기존에는 개발용 결제 처리에서만 로그를 저장했고 주문 생성 시에는 최초 로그를 생성하지 않았다.
- 주문 생성 시 `PENDING` 로그를 저장하고, 조회한 `OrderLog`를 `BuyerOrderLogResponse`로 변환해 상세 응답에 포함했다.
- 기존 주문처럼 과거 로그가 없는 데이터도 현재 `OrderStatus`를 기준으로 도달한 단계까지 표시하고, 실제 로그가 있는 단계에는 처리 일시와 처리자를 함께 표시했다.
