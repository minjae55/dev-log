## Learned

- Toss 결제창을 열기 전에 내부 주문번호가 필요하므로 주문을 먼저 생성하는 구조 자체는 자연스럽다. 다만 외부 결제창 진입과 실제 결제 완료는 같은 사건이 아니므로 중간 상태를 고려해야 한다.
- 같은 결제 요청이 반복돼도 결과가 달라지지 않도록 만드는 멱등성은 네트워크 재시도뿐 아니라 사용자가 결제창을 닫고 다시 시도하는 상황에서도 필요하다.
- 프론트의 `sessionStorage`만으로 기존 주문번호를 재사용하면 새로고침이나 다른 기기에서의 재시도를 처리할 수 없다. 서버가 기존 `PENDING` 주문을 조회해 재사용하는 방식이 더 안정적이다.
- `AuthUser`는 인증 정보의 요약이고 JPA `User`는 연관관계 저장에 필요한 엔티티다. 조회 조건에 ID만 필요하면 재조회하지 않고, 주문 생성·서명·상태 이력처럼 실제 엔티티가 필요할 때만 `UserReader`를 사용해야 한다.
- 가상계좌 발급 성공과 입금 완료는 다른 상태다. 결제 승인 응답만으로 주문을 바로 확정할지, 입금 완료 웹훅을 기준으로 확정할지 결제수단별 상태 흐름을 분리해야 한다.

## Troubleshooting

- 샘플 결제를 처음 시도할 때 `orders`에 `PENDING` 주문이 생성된 뒤 Toss 결제창이 열렸다. 결제창을 닫고 다시 결제하면 `validateDuplicateOrder()`가 기존 주문을 활성 주문으로 판단해 `SAMPLE_ORDER_ALREADY_EXISTS`를 발생시켰다.
- 중복 주문 검증은 결제 완료 주문을 다시 만드는 것은 막았지만, 결제에 실패하거나 중단된 주문을 재사용하는 흐름은 고려하지 못했다.
- 단순히 프론트에서 주문번호를 보관하거나 실패할 때 주문을 삭제하는 방식도 검토했지만, 브라우저 종료와 네트워크 단절 상황에서는 정리 요청을 보장할 수 없었다.
- 기존 `PENDING` 샘플 주문이 있으면 새 주문을 만들지 않고 해당 주문번호를 반환하고, 이미 결제된 활성 주문이 있을 때만 중복 주문 예외를 반환하는 방향으로 수정하기로 했다.
- 동시에 두 요청이 들어오는 상황까지 막으려면 조회 후 생성만으로는 부족할 수 있으므로, 거래 식별 키의 유니크 제약이나 잠금 적용 여부도 함께 검토할 예정이다.
